# 消息中心：多渠道上报与转发

| 项 | 值 |
| --- | --- |
| 状态 | 已确认，按此开工 |
| 日期 | 2026-11-22 |
| 范围 | 需求。微信模块改动仍不在本仓库 |
| 相关仓库 | 本仓库 `message-center`；微信模块在 `WechatMsgHook-v1` |

## 一句话

msg-hook 只把微信里收到的消息报给消息中心。消息中心再按规则转发。上报和转发都是渠道，而且是多对多：这一期上报有微信和 Webhook，转发有 inwit、Vital、aimo。以后加渠道时不改这条模型。

## 已经定的

1. 转发渠道这一期是三个：inwit、Vital、aimo。再加渠道时走同一套连接和规则，不把令牌写回模块。
2. 上报渠道这一期是两个：微信模块，以及 Webhook。账号下是同一套密钥，不按渠道拆开。用户自己决定把哪一把放到微信、Webhook，或两处复用。每把密钥有名称和备注。密钥不绑定某一个 wxid。
3. 收发多对多。多台手机、多个调用方共用一套规则。一条消息可以同时进多个目的地。一个目的地也可以接收多个来源。
4. 规则可以标成独占。默认不独占。现在的 aimo 群用独占保住「整群只进 aimo」。
5. 不做自动回复。模块里现在的 `a` → `hello` 在切换后停掉。
6. 自己发出的消息不上报。
7. 一个登录用户可以挂多枚 Vital 令牌，也可以挂多枚 inwit 令牌、多枚 aimo 令牌。现在的两个微信身份可以继续进两个不同的 Vital 用户。
8. 图片和语音的开关做在目的地连接上，默认关。打开后这一期记为等待转存，不传字节。S3 转存以后再做。
9. inwit 用现成的 `POST /api/open/documents` 写 markdown，令牌是 `iwt_`，不指定 topic。
10. 上报正文保留，这一期不自动删除。

## 现在的问题

策略写在 `vital.local.properties`，打包进 APK。

| 写死的东西 | 现在的位置 | 后果 |
| --- | --- | --- |
| 微信身份 → `vt_` 令牌 | `VITAL_ACCOUNT_<wxid 或房间>` | 换令牌、加一个人，都要重新打包、安装、重启微信 |
| 群 → aimo 的 uid 和 `aimo_tk_` | `AIMO_BIND_<房间>` | 同上。这条群规则会吃掉发送者的 Vital 规则 |
| 只收别人发来的；文本和链接才转发；语音和图片跳过 | `MemoSyncService` | 改过滤条件要发一版模块 |
| 链接抓正文 | 模块在微信进程里轮询 Vital，最多约 90 秒 | 抓取占着微信进程里的队列 |
| 自动回复 `a` → `hello` | `HookEntry` 常量 | 切换后删除，不再有替代 |

已经在用的路由（令牌不写在这里）：

| 微信身份 | 现在的去向 |
| --- | --- |
| `wxid_8139281393915`（未命铭） | 一个 Vital 用户的收集箱 |
| `wxid_ddhq38ui6s5j22` | 另一个 Vital 用户的收集箱 |
| `52737264862@chatroom` | aimo，整群，不再进 Vital |
| 别的群里如果发送者是上面两个 wxid | 按发送者进对应 Vital |

模块没有设置页。目的地令牌打进 APK 之后，反编译就能读到，而且那枚 `vt_` 或 `aimo_tk_` 能操作整个目的地账号。

## 目标

1. 微信模块只上报。它不选择目的地，不保存 `vt_`、`iwt_`、`aimo_tk_`，不调用 Vital、inwit、aimo。
2. Webhook 是第二条上报渠道。调用方 POST 一条规范化消息，走同一套规则。
3. 规则按发送者、群、以及可选的上报渠道来匹配。命中的规则全部转发，除非某条打开了独占。
4. 三个转发渠道这一期都能收文本和链接。图片和语音看该连接的开关，默认不收。
5. 消息中心是多用户的。每个人只看见自己的钥匙、连接、规则和消息。
6. 登录支持邮箱密码，也支持统一账号（与 inwit 同一套 Keycloak，独立 client）。没配齐时登录页不出现这个入口。
7. App Key 只能上报微信消息。Webhook 钥匙只能打自己的那个地址。两种钥匙都不能改规则，也不能读出目的地令牌。
8. 换目的地令牌、改规则，不需要重新打包模块。

## 这一期不做

- 不做 S3 转存，不在模块里上传图片或语音字节。开关可以保存，打开后的投递停在「等待转存」。
- 不做自动回复，模块也不再本地回复。
- 不做第四个转发渠道，也不做第三种上报渠道。模型要能加，代码这一期只接上面列出的。
- 不做模块里的设置页。App Key 和消息中心地址仍在打包时写入。吊销 App Key 后要换一版模块才能恢复微信上报。换目的地令牌不需要换模块。
- 不补历史消息。
- 不把消息自动转成 Vital 任务，也不指定 inwit 的 topic。
- 不和 inwit、Vital、aimo 共用数据库，不复用它们的 OIDC client。
- 不做微信模块以外的移动端 App。

## 谁在用

| 角色 | 做什么 |
| --- | --- |
| 登录用户 | 登录，生成 App Key 和 Webhook，保存 inwit / Vital / aimo 连接，编写规则，查看投递 |
| 微信模块 | 一台手机一把 App Key，上报收到的消息 |
| Webhook 调用方 | 用一把账号密钥向 Webhook 地址上报。可以和微信模块复用同一把 |
| inwit、Vital、aimo | 目的地。消息中心用用户保存的令牌去写 |

一个登录用户一次会话只有一个账号。换消息中心账号要退出再登录。一个用户名下可以有多把上报钥匙、多条目的地连接。

## 渠道

### 上报

| 渠道 | 这一期 | 凭证 |
| --- | --- | --- |
| 微信 | 做 | 账号密钥，`mck_`。用户选择放到模块里 |
| Webhook | 做 | 同一套 `mck_`。用户可以复用微信那一把，也可以另建一把，用备注区分 |
| 以后的渠道 | 只留模型 | 仍用账号密钥，不新发明一种钥匙 |

微信侧的身份在消息里：群看 `talker`，发送者看正文前缀或单聊的 `fromUser`。钥匙本身不代表某个 wxid，也不代表某一个上报渠道。

Webhook 的发送者和房间是调用方给出的字符串。规则用同一套字段匹配。想让 Webhook 和某条微信规则走同一条，就把发送者或房间写成同一个 id。

### 转发

| 渠道 | 凭证 | 这一期写入 |
| --- | --- | --- |
| Vital | `vt_`，一个用户可有多枚 | 收集箱。文本直接写；合法链接先 extract-job，失败则标题加原链接 |
| aimo | `aimo_tk_`，一个用户可有多枚 | 个人笔记接口 `POST /api/v1/memos`。分类名「微信收集」。不走 BA 接口 |
| inwit | `iwt_`，一个用户可有多枚 | `POST /api/open/documents`，markdown。链接带 `sourceUrl` |
| 以后的渠道 | 连接上的密文 | 新增一种适配器，规则不用改字段 |

图片、语音：连接上两个布尔值，默认都是关。关着时这种消息对该连接记「已跳过」。打开后这一期记「等待转存」，等 S3 模块来了再真正上传。文本和链接不受这个开关影响。

## 场景

### 登录

- 邮箱和至少 8 位密码，可以注册、登录、退出。
- 统一账号配齐后，登录页出现「使用统一账号登录」。完成后进入消息中心已登录状态。
- 同一个 `(issuer, sub)` 再次登录，进入原来的用户。不用邮箱把统一账号并进已有的密码账号。
- 只配了一部分统一账号参数时，入口不出现。

### 上报凭证

- 密钥属于登录用户，不分成微信钥匙和 Webhook 钥匙。创建时填写名称和备注，例如「主力机」或「报警 Webhook」。
- 创建时能复制完整密钥，之后列表只显示预览和备注。登录后可以再次显示，也可以吊销。
- 同一把密钥可以同时用于微信上报和 Webhook 上报。用户也可以为不同渠道各建一把。
- 吊销立即生效，只影响这一把。其它密钥继续可用。
- 这些密钥上报进来的消息都归这个用户，走他的那一套规则。

### 目的地连接

- 添加时选择渠道，粘贴对应前缀的令牌，并可写显示名。
- 保存前用令牌向该渠道要一次「我是谁」。Vital 是 `GET /api/v1/auth/me`，aimo 是 `GET /api/v1/user/info`，inwit 是 `GET /api/auth/me`。失败不保存。
- 界面能看出接的是哪个账号，不回显完整令牌。
- 某次转发得到 401，只把这一条连接标成失效并停止使用它。别的连接继续。
- 每条连接有图片开关和语音开关，新建时都是关。

### 规则

一条规则属于一个登录用户：

- 名称、是否启用、可选的独占
- 匹配：可选的上报渠道（不填表示微信和 Webhook 都可以）、可选的房间、可选的发送者。两个身份都空表示匹配该用户全部上报，界面要写明范围很大
- 房间和发送者都填时，两个都要命中
- 目的地：某一条已保存的连接

匹配看的是规范化之后的消息，不是模块自己选的目的地。

- 微信群消息先拆前缀（先 `:\n`，否则第一个 `:`；前缀须像 `wxid_` 或带 `@`）。发送者是前缀，房间是 `talker`
- 微信单聊用 `fromUser`，空了再用 `talker`
- Webhook 直接用调用方给的发送者和房间
- 所有命中的启用规则都各产生一条投递
- 其中若有独占规则命中，只保留这些独占规则，非独占的不再投递。多条独占同时命中时，这几条都投
- 没有命中：消息留下，状态为未匹配，不调用任何目的地

把现在的两个人配成两条发送者规则，目的地各选一枚 Vital。`52737264862@chatroom` 配一条只填房间的 aimo 规则，并打开独占。这样群消息只进 aimo；别的群里这两个发送者仍进各自的 Vital。

### 微信模块上报

1. 丢掉自己发出的（`isSend != 0`）。
2. 丢掉不认识的类型。认识的是文本（type 1）、链接（type 低 16 位为 49）、现在标成图片的那些 type，以及 type 34 语音。视频和表情不上报。
3. 文本和链接正文为空则丢掉。图片和语音没有正文也要报一条，不带文件字节。
4. 三条 Hook 打到同一条消息时，模块保留进程内去重，避免短时间打三次网。这只减少请求。
5. 用 App Key POST 原始字段：类型、talker、fromUser、原文、msgSvrId、createTime、模块版本。不附带目的地和任何目的地令牌。
6. 消息中心接受之后模块即完成。它不等待目的地抓链接。

没有钥匙、地址不是 https origin、或者这一进程已经 401：Hook 照常，只是不上报。

### Webhook 上报

调用方 POST 到账号的 Webhook 地址，带上一把账号密钥。正文至少要有事件 id、类型、发送者、文本或链接。房间可空。不传「发给哪个目的地」。同一用户下，事件 id 重复时当作同一次上报。

### 转发

消息先落库，再由消息中心转发。微信进程不被链接抓取拖住。

- 一条消息命中几条规则，就有几条投递。各条独立成功或失败。
- 文本和链接按上面三个渠道各自的写法发送。
- 图片和语音：连接关着则该条投递跳过；开着则等待转存，这一期不发出。
- 同一条上报重复到达时，不新增加投递，目的地侧也不再写一次。
- Vital 链接仍按它自己的「同一个规范 URL 一行」合并。
- 控制台能看到每一条投递的渠道、状态、目的地记录 id、HTTP 状态和 `error.code`。看不到令牌，也看不到对方错误体里的正文详情。
- 网络错误和 502/503/504 会再试。401 只停那一条连接。400、404、409、422、429 不重试。

## 控制台

- 接入：密钥列表，含名称和备注
- 连接：inwit、Vital、aimo，以及图片/语音开关
- 规则：匹配条件、目的地、独占
- 消息：来源渠道、发送者、房间、类型；下面列出每条投递的结果

## 验收

1. 未登录不能生成钥匙、不能保存连接、不能改规则、不能看消息。
2. 用户 A 的钥匙、连接、规则、消息，用户 B 看不到，也不能用 A 的钥匙写入 B 的数据。
3. 统一账号未配置时没有该按钮，也没有发往 Keycloak 的请求。配齐后能进入同一个用户。
4. 吊销一把密钥后，微信和 Webhook 用这把密钥都返回 401。同一用户的其它密钥仍可上报。密钥不能访问规则或连接接口。
5. 同一把密钥既能上报微信消息，也能上报 Webhook。备注只用于辨认，不参与鉴权。
6. 两个微信身份各配一枚 Vital。各自发来的文本进各自的收集箱。
7. 同一条消息配了 Vital 和 inwit 两条规则时，两边都有记录。
8. aimo 房间规则打开独占时，该群消息只进 aimo，不进发送者的 Vital。关掉独占后，两条都进。
9. 没有规则的消息在控制台是未匹配，三个目的地都不新增。
10. 微信三条 Hook 重复上报，每个目的地只有一条。Webhook 用同一个事件 id 再 POST 一次，也只有一条。
11. 合法链接由消息中心去处理。模块日志里没有 Vital 的 extract 轮询，也没有 aimo 或 inwit 的请求。
12. 新建连接的图片和语音开关是关。图片上报后，对应投递是跳过，目的地没有新文件。
13. 把开关打开后，投递变成等待转存，这一期仍然没有文件上传。
14. 模块包里没有 `vt_`、`iwt_`、`aimo_tk_`。只有消息中心地址和 App Key。
15. 在控制台更换一枚目的地令牌后，不重装模块，新消息进新令牌对应的账号。
16. 自己发出的微信消息不会出现在消息中心。

## 模块侧以后要改的边界

确认后另做，不在本仓库改微信 Hook。

模块保留：拦截、字段读取、进程内去重。

模块删除：Vital、aimo 的地址与令牌、白名单、收集箱和笔记的字段组装、extract 轮询、自动回复常量。
